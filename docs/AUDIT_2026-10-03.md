## Findings and automatic remediation

### F1 — backend validation response privacy (high, reproduced)

At the original implementation, invalid password objects and unexpected request fields received FastAPI HTTP422 details containing submitted values. Error responses lacked `Cache-Control: no-store`. SecretStr alone did not sanitize validation inputs. A sensitive extra field name could also be echoed through the error location.

Remediation PR #14 returns only `{"detail":"Invalid request"}` with HTTP422/no-store. Seven regressions cover invalid password/username types, extra values, sensitive extra field names, missing fields, invalid body shape and malformed JSON. Invalid requests never construct an Xtream client. Valid authentication behavior is preserved.

Local: 69 passed, one PostgreSQL-only test explicitly skipped. GitHub PostgreSQL CI `37078597908`, job `111073945949`: 70 passed, Ruff, Alembic and secret scanning SUCCESS. Implementation SHA: `eb0bdbc2afa305d1011e5c96a6a90c56f479367b`. Final result/timestamp-only head `9f84e6c5789f1c9f019f5eccce570076c78e1e25` also passed Backend CI `37080066858`. Merge remains a Human Gate.

### F2 — stale Android asynchronous responses (medium, code defect with regression)

Catalog clear/logout previously cleared state without invalidating in-flight requests. A delayed old success or error could repopulate the cleared catalog. Loading was set only inside the scheduled coroutine, allowing queued duplicate loads. Series detail guarded only by ID; an older result for the same ID could overwrite the newest request after clear/reopen.

Remediation PR #15 adds generation checks before work and after suspension, guards publication/failure and marks catalog loading synchronously. Four regressions exercise queued clear, late category failure, old account streams after a new load, and stale same-series detail after clear/reopen. The EPG and Search controllers already had generation guards and were preserved. Implementation SHA `d15da5baf271f7f0fc08405b7fc2c01d9feb2bd4`: Android CI `37078859769` (JVM/lint/build and API36 phone regression) and Backend CI `37078859820` both SUCCESS. Phone job `111076348740` completed with PHONE_DEVICE_PROOF=PASS and PHONE_CRASH_ANR=NONE. Final result/timestamp-only head is `f30faa0080fef20f4e477d219630914d8656422d`; it does not change Android executable sources.

### F3 — Settings proof was compiled but not executed (medium)

Original API36 selection explicitly excluded `VpnSettingsDpadTest`; API24 only ran startup/native/identity/manifest tests. Its TV-only assumption would skip on a phone emulator. Green CI therefore did not prove the requested Settings touch/focus contract.

PR #13 remediation adds a touch action test and explicitly supplies TV UI configuration for a simulated-TV D-pad test on the API36 emulator. Its first execution ran both tests: touch passed, initial D-pad focus failed because visual TV configuration alone did not switch the phone out of touch input mode. The next execution showed that requesting input mode in the initial composition SideEffect was too early: the Android request returned false during view attachment. Recovery now mounts ordinary Settings first, requests real keyboard mode from runOnIdle after attachment, then enables simulated TV configuration to run autofocus. Every focus/click assertion is preserved. The official [InputModeManager contract](https://developer.android.com/reference/kotlin/androidx/compose/ui/input/InputModeManager) documents this request and its Boolean success result. Recovery counters and the failed run are recorded in the task checkpoint; unchanged failing work was not retried. The CI now runs that class. It still excludes the separate physical/TV-only test classes. No system VPN dialog is physically accepted, no WireGuard configuration is built, and no tunnel is activated by these tests.

### F4 — narrow scanner metadata exception (reviewed)

PR #13's scanner filter allows only Hex High Entropy String findings on recognized control-record SHA fields with exact lowercase 40/64-character hex values. Other finding types/fields/lengths remain fatal. Local positive and negative probes verified this boundary; no whole-directory exclusion was added. The same helper is reused by independent remediation PRs because main's scanner otherwise rejects their authorization SHA metadata. This helper is not a substitute for historical secret auditing or a trusted branch policy.

## Preserved safety contracts

- Mega token remains backend-only; no upstream password column in mapping.
- Mapping host is authoritative; no inferred/rewritten DNS/subdomain.
- Backend never proxies video; playback remains direct provider-to-client.
- Backend outbound validation rejects private destinations and binds the transport to validated public IPs while preserving TLS hostname verification.
- Backend and Android redirects remain disabled. Providers that require redirects need secure compatibility proof; redirects were not enabled speculatively.
- Android backend URL requires HTTPS. Provider HTTP is intentionally preserved under the current proof contract; production cleartext policy is still an explicit decision.
- IPTV credentials and WireGuard identity use separate encrypted persistence/Keystore aliases. Room contains media metadata/profile digests rather than credential-bearing playback URLs.
- 004B identity is installation-scoped, survives IPTV logout, and corruption fails closed without silent rotation.
- Official VPN service has BIND_VPN_SERVICE and SUPPORTS_ALWAYS_ON=false. No UP call, peer or real Config was added.

2. **WireGuard runtime gate:** rollback plan, current OVH service/network audit and explicit permission for test peer/server/network actions before real tunnel work. No throughput/capacity claim follows from VPS vCore/RAM specifications.
3. **Provider/device evidence:** later Phase 3 real-provider tests and physical-TV tests remain not separately certified. Existing authentication proof does not certify playback/EPG/Catch Up.
4. **Windows stage:** no implementation exists. Opening that staged product scope requires the corresponding bounded order after prerequisite stages.
5. **Production security:** rate limiting and bounded request/provider-response size controls, dependency vulnerability assessment, operational health/telemetry, safe deployment configuration, privacy policy and restore tests remain launch requirements. No current CVE clearance is claimed from version pins or secret scanning.
6. **Build configuration:** default Android API base is `https://pink-api.invalid`; CI does not create a production-capable customer build or prove deployed HTTPS connectivity.
7. **GitHub governance:** main is unprotected; no target-repository trusted v2 control gate exists. Installing governance is separate from application correctness and does not authorize modifying the control repository.
8. **CI evidence durability:** APK, unit/instrumentation reports and logs are not published as durable downloadable artifacts in the observed Android workflow. Release/signing and artifact retention need their later hardening order.
9. **Documentation:** distinguish merged implementation, automated emulator proof, historical live authentication, and uncertified provider/physical-device evidence. The old OVH PR must not overwrite the newer infrastructure narrative.
10. **Runtime limits:** this execution did not inspect the VPS filesystem, current service health, real secrets, customer data, firewall, VPN peers or backups. Repository descriptions of runtime are historical snapshots, not a live operational certification.
